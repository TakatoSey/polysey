# PolyCopy

Однопользовательский Telegram-бот для paper-копитрейдинга Polymarket.

## Что есть сейчас

- RTDS для обнаружения сделок отслеживаемых лидеров и независимый Data API для восстановления пропусков;
- свежие REST-снимки CLOB для исполнения (неполные WebSocket-дельты не используются для fills);
- FAK market execution с глубиной книги и partial fills;
- fee schedule рынка из CLOB API; при недоступности используется оценочный fallback, поэтому точность комиссии в этом случае не гарантирована;
- отклонение цены в абсолютных центах и отдельная защита от входа после резкого падения;
- проверка минимального размера CLOB-ордера;
- paper-позиции, баланс, ордера и история;
- пропорциональные продажи только собственных долей соответствующего лидера; сохранение неисполненного остатка выхода;
- адаптивный размер BUY: процент наших свободных денег, относительный размер серии покупок лидера и доступная цена;
- stop-loss, take-profit и trailing-stop;
- аварийные `/pause` и `/resume`;
- PostgreSQL и восстановление состояния после перезапуска.

Реальные ордера, приватные ключи, CLOB-аутентификация и кошельки намеренно не подключены.
Это **paper-версия**, не готовый live-trading продукт. Прохождение тестов не
доказывает точность исполнения на бирже или будущую прибыль.

## Запуск на VPS

```bash
git clone https://github.com/TakatoSey/polysey.git polycopy
cd polycopy
cp .env.example .env
nano .env
docker compose up -d --build
docker compose logs -f bot
```

Read-only settlement audit (uses positions from the database when no IDs are supplied):

```bash
docker compose exec bot python -m app.audit
```

Сверка учёта без сетевых запросов и без записи в базу:

```bash
docker compose exec -T bot python -m app.ledger_audit
```

Показывает баланс, восстановленный из ордеров, расхождения по деньгам и shares,
распределение PNL по лидерам и незавершённые выходы. Малые расхождения возможны
из-за округлённой средней цены старых fills. При неоднозначных старых продажах
появится предупреждение; команда не переписывает историю.

В `.env` укажи токен Telegram-бота и свой numeric Telegram ID. Секреты не отправляй в чат.

## Команды

`/start`, `/status`, `/settings`, `/leaders`, `/addleader 0x...`, `/removeleader 0x...`, `/portfolio`, `/orders`, `/risk TOKEN sl=0.2 tp=0.25 trail=0.1`, `/setsize 5`, `/setmax 10`, `/setslippage 5`, `/pause`, `/resume`.

Основной интерфейс — редактируемая Telegram-панель. В разделе «Лидеры» можно добавить любое количество адресов, включать/выключать копирование и удалять лидера; переключение экранов редактирует одно сообщение. Входящие команды и адреса удаляются best-effort, поэтому чат не засоряется. Новые сообщения бот отправляет только для торговых уведомлений.

В адаптивном режиме `/setmax 30` задаёт общий максимум **серии входа с комиссиями**.
`/setsize 5` сохраняет настройку только для классического режима: это больше не
скрытый потолок каждой адаптивной покупки. Действующий максимум хранится в базе:
изменение `MAX_TRADE_SIZE` в `.env` не перезаписывает его у существующего аккаунта.

Первый лидер из `.env.example` добавляется автоматически, но его адрес можно изменить в `.env`.

## Адаптивный размер позиции

При `SMART_SIZING_ENABLED=true` бот сравнивает размер текущего входа трейдера
с его обычными входами, а бюджет берёт из **наших свободных денег**. Стоимость
открытых позиций трейдера не считается его балансом; точный капитал лидера модель
не определяет. Это правило распределения бюджета, а не гарантия прибыльности.

Несколько BUY одного трейдера в одном token_id объединяются в серию по фиксированным
окнам `SMART_SIZING_BURST_SECONDS` секунд исходного времени сделки (по умолчанию 2).
Такая группировка — эвристика: близкие сделки по разные стороны границы разделятся,
а независимые покупки внутри окна объединятся. Это не восстановление настоящего
order ID. Бот **не ждёт** окончания окна: первый доступный объём исполняется сразу,
следующие части могут только дополнить общий бюджет. SELL закрывает серию и не
позволяет поздним старым BUY снова расходовать её бюджет.
Фрагменты, уже полученные к завершению подготовки, исполняются одной FAK-заявкой
по средневзвешенной цене лидера. Пришедшие позже могут сформировать добавку в
пределах того же общего бюджета. Получить ровно один ордер на все будущие
фрагменты без ожидания невозможно. Идентификатор каждого исходного фрагмента
сохраняется атомарно с результатом: повтор через REST или после перезапуска
не выдаёт новый бюджет.

Обозначения и формула:

```text
C = наши свободные деньги в начале серии
r = COPY_BALANCE_PCT (по умолчанию 0.05)
L = сумма покупок лидера в этой серии, без комиссий
T = типичный размер исторической серии лидера
V = средняя цена лидера в текущей серии: сумма(size × price) / сумма(size)
P = доступная нам цена покупки

База       = C × r
Масштаб    = min(SMART_SIZING_MAX_MULTIPLIER, L / T)
Цена       = min(1, V / P)
Цель       = min(База × Масштаб × Цена, максимум серии из базы)
Добавка    = max(0, Цель − фактически потрачено в серии с комиссиями)
```

Затем добавка ограничивается текущими свободными деньгами и остатком лимита на
исход `MAX_OUTCOME_EXPOSURE`; в адаптивном режиме оба лимита учитывают комиссию.
Расчёт не увеличивает риск из-за более дешёвой цены и не считает цену вероятностью
победы. Для глубины стакана продолжает действовать обычный лимит slippage;
уменьшение бюджета не разрешает покупку за его пределами. Реальные shares зависят
от цен по уровням стакана и частичного исполнения.

Например, при `$150` свободных денег база составляет `$7.50`. Если типичный вход
лидера — `$20`, серия на `$10` даёт цель `$3.75`, на `$20` — `$7.50`, а на `$40` —
`$15.00` при одинаковой доступной цене и достаточных лимитах. Если в серии уже
потрачено `$3.75`, увеличение её цели до `$7.50` разрешает ещё `$3.75`, не второй
полный бюджет. При средней цене лидера `$0.50` и нашей `$0.52` цель `$7.50`
уменьшается до примерно `$7.21`. Это общие суммы **включая комиссию**, не чистый notional.

Мелкий остаток ниже `MIN_COPY_NOTIONAL` или минимального числа shares из CLOB
не увеличивается принудительно. Он учитывается при следующем BUY той же серии;
если продолжения нет, покупки на эту сумму не будет. Пустой стакан, превышение
slippage или отсутствие бюджета по-прежнему могут привести к пропуску.

### Откуда берётся типичный вход

Статистика использует последние 500 записей activity, не старше семи дней.
Исторические BUY группируются так же, как текущие; незавершённые и текущие
копируемые окна исключаются. Типичный размер — среднее сумм серий после удаления
по 10% самых маленьких и больших значений (для короткой выборки округление может
не удалить ни одного). Это не простое среднее отдельных fills и не показатель
капитала человека.

Нужны минимум `SMART_SIZING_MIN_SAMPLES` законченных серий (по умолчанию 3).
Пока данных недостаточно, новые BUY пропускаются с понятной причиной, а карточка
лидера показывает сбор статистики. Продажи уже имеющихся позиций от этого не
отключаются. В карточке также видны типичный размер, число серий и время обновления
в UTC. Профили обновляются при запуске и раз в
`SMART_SIZING_STATS_REFRESH_SECONDS` секунд (по умолчанию сутки), без дополнительных
сетевых запросов на пути исполнения новой сделки. Для очень активного лидера 500
записей могут покрывать значительно меньше семи дней.

База, выбранная статистика и фактические расходы начавшейся серии сохраняются
вместе с учётом ордеров. Перезапуск и повторное получение уже обработанного события
не должны выдавать серии новый бюджет. Максимум `SMART_SIZING_MAX_MULTIPLIER=3`
ограничивает усиление относительно базового процента; ограничения свободных денег,
серии и открытой себестоимости исхода продолжают действовать независимо от него.

Для возврата к классическому алгоритму: `SMART_SIZING_ENABLED=false`. Только там
используются фиксированный предел `/setsize` и `LEADER_ORDER_SCALE`; менять режим
нужно с пересозданием контейнера. Подробное объяснение доступно в Telegram:
«Настройки → Размер сделки».

## Задержка копирования

Рекомендуемые параметры `.env` для VPS:

```dotenv
POLL_INTERVAL_SECONDS=0.5
COPY_LATENCY_SECONDS=0
MAINTENANCE_INTERVAL_SECONDS=2
COPY_PREPARE_CONCURRENCY=8
COPY_QUEUE_LIMIT=256
RTDS_ENABLED=true
MAX_SIGNAL_AGE_RTDS_SECONDS=2
MAX_SIGNAL_AGE_REST_SECONDS=5
DEFAULT_SLIPPAGE_CENTS=5
EXIT_RETRY_ENABLED=true
EXIT_RETRY_SECONDS=1
```

После изменения настроек: `docker compose up -d --build bot`. Обычный `restart`
не подхватывает изменённые environment-переменные контейнера.

Опрос каждого лидера работает независимо от исполнения, выплат и стопов. Медленный
ответ одного лидера не останавливает следующие опросы других. Подготовка разных
сделок и ожидания `seconds_delay` идут параллельно. Для пары «лидер + token_id»
сохраняется порядок BUY/SELL; медленный вход другого лидера не блокирует выход
из уже имеющихся долей. Одновременные запросы одинаковых метаданных объединяются
без кэширования открытого/закрытого статуса рынка.
Выходы имеют отдельные слоты подготовки и приоритет записи в учёт. SELL отменяет
ещё не завершённую подготовку устаревшего BUY этого лидера; BUY регистрируется
как пропущенный, а не исполняется перед уже известным выходом.

Изменения баланса, позиций и выплат сериализованы внутри одного процесса. После
ожидания заново проверяются пауза, активность лидера, доступные деньги и доли.
Стакан загружается параллельно подготовке; если после задержки или очереди
локальный снимок старше 250 мс, он запрашивается повторно. Обновление не держит
блокировку баланса. Возраст самого снимка на стороне API этим не гарантируется.
Неиспользуемый неполный WebSocket-кэш стакана не запускается и не расходует CPU
на обработку подписок. RTDS обнаружения сделок от него не зависит.
Запускайте **один экземпляр bot** на эту базу, не несколько реплик: PostgreSQL
advisory lock не позволит второму исправному экземпляру одновременно запуститься.

`COPY_LATENCY_SECONDS` — только добавочная искусственная задержка. Сеть уже занимает
реальное время; обязательный `seconds_delay` рынка остаётся независимо от настройки.
Slippage и проверки ликвидности ради ускорения не отключаются.

`DEFAULT_SLIPPAGE_CENTS=5` и команда `/setslippage 5` означают **пять центов**
(`$0.05`), не 5% от цены. Для BUY лидера по 17¢ допустимый ask — 12–22¢:
выше 22¢ превышен предел покупки, ниже 12¢ срабатывает отдельный фильтр
`entry_price_drop`. Этот фильтр — защитная эвристика, а не доказательство плохой
сделки. В адаптивном режиме дополнительно учитывается VWAP серии. Для SELL
по 17¢ нижний предел — 12¢; любая более высокая цена допускается.

BUY из REST старше `MAX_SIGNAL_AGE_REST_SECONDS` (по умолчанию 5 с) не догоняется;
RTDS имеет отдельный предел 2 с. Возраст проверяется при получении и перед
исполнением, включая подготовку, очередь и обязательную задержку биржи. Поэтому
рынки с долгим `seconds_delay` могут не пройти строгий возрастной фильтр. Часы
VPS должны быть синхронизированы. Это защита от запоздалой покупки, **не ускорение
публикации источником**; доля скопированных сделок может уменьшиться.

### Надёжные выходы

Новый SELL создаёт `exit_intents`: оставшиеся shares, ценовой предел, лидер и
конкретная открытая позиция. Малые фрагменты продаж накапливаются до минимального
размера заявки. Частичное исполнение уменьшает остаток ровно на исполненные доли.
Повторы используют свежий стакан, параметры рынка и комиссию; ожидание увеличивается
от `EXIT_RETRY_SECONDS` до 30 секунд при повторных неудачах. Ценовой предел сам
не ухудшается; изменить его может новый SELL лидера. Без подходящих bids или при
остатке ниже минимума выход может остаться незавершённым до следующего сигнала
или выплаты. Гарантии закрытия нет.

При `/pause` или выключении лидера повторы приостанавливаются. Новые BUY этого
лидера в том же исходе не открываются, пока висит его выход. Выплата отменяет
оставшиеся запросы выхода; риск-продажа корректирует их остатки. Поздний SELL
старше уже скопированной новой покупки её не продаёт. Остатки и пределы видны
над историей ордеров. Старые отклонённые SELL не превращаются автоматически в
новые заявки при обновлении: для их ретроспективного исполнения нет надёжной
информации о намерении и жизненном цикле позиции.

### Обновление существующей установки

Сначала остановите **старый** bot и сделайте резервную копию базы. Не удаляйте
Docker volumes и не запускайте старую версию рядом с новой: в старой нет защиты
advisory lock. Новая версия добавляет таблицы автоматически; деньги и старые
ордера не переписываются. При первом запуске добавляются канонические алиасы
старых событий, чтобы смена формата идентификаторов не повторяла покупки.

```bash
cd ~/polycopy
docker compose stop bot
docker compose exec -T db pg_dump -U polycopy -d polycopy -Fc > "backup-$(date -u +%Y%m%dT%H%M%SZ).dump"
git pull --ff-only
# Обновите только нужные строки .env по .env.example, сохранив свои секреты.
docker compose up -d --build bot
docker compose exec -T bot python -m app.ledger_audit
```

Уберите старый `DEFAULT_SLIPPAGE_BPS`: он больше не участвует в исполнении.
`DEFAULT_SLIPPAGE_CENTS` инициализирует отдельную настройку `execution_policy`
один раз; далее используйте `/setslippage 5`. Старое поле `accounts.slippage_bps`
сохраняется для совместимости истории, но не переиспользуется с другими единицами.
Команда меняет лимит **новых сигналов**, не уже сохранённых выходов.

Проверка на VPS после новых сделок:

```bash
docker compose logs --since=10m bot | grep -E 'rtds_health|rtds_trade_stream|copy_latency|copy_batch|copy_rejected|exit_filled|worker_failed|copy_queue_full'
```

В `copy_latency`: `source_age_seconds` — возраст сделки уже при получении HTTP-ответа
(включает публикацию/индексацию, ожидание опроса и сеть; timestamp имеет секундную
точность); `prepare_ms` — время от получения до готовности метаданных и завершения
ожиданий; `after_prepare_ms` — ожидание порядка, стакан и запись; `bot_ms` — всё время
от получения до сохранения результата. `exchange_delay_seconds` показывает
обязательное ожидание рынка. Эти замеры относятся и к пропускам, не только к fills.

Это не обещание нулевой задержки или live-эквивалентности симуляции. Источник —
публичная activity (RTDS, если действительно поступают подходящие payloads, и
[Data API activity](https://docs.polymarket.com/api-reference/core/get-user-activity)),
а не чужой приватный поток ордеров. Сообщение `connected` не доказывает получение
сделок: смотрите `rtds_trade_stream_ready` и счётчики `rtds_health`.
Источник может публиковать сделки с задержкой;
ускорение цикла не устраняет её и не гарантирует прибыль. После длительного простоя
текущий poll видит последние 500 записей на лидера, не неограниченную историю.
Ограничение очереди не создаёт fake fills: незавершённые события повторно проверяются
через REST, пока они доступны в этом окне. Для большого количества лидеров нужно
учитывать общие [лимиты API](https://docs.polymarket.com/api-reference/rate-limits).

Paper не воспроизводит очередь matching engine, конкуренцию за ликвидность,
реальное подтверждение ордеров, скрытый объём и воздействие собственных заявок
на последующие снимки стакана. Оценочный fallback комиссии также остаётся
оценкой. До live необходим отдельный исполнитель с аутентификацией, точными
правилами округления и комиссиями, сверкой фактических fills, восстановлением
после разрыва связи и тестами с реальным CLOB. Сверяйте интеграцию с документацией
[ордеров](https://docs.polymarket.com/trading/manage-orders) и
[комиссий](https://docs.polymarket.com/trading/fees), не с доходностью лидера.
